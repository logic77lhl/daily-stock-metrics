# 每日市场指标（A股 / ETF / 港股通）

每日自动获取 **A股市值前100**、**场内规模前100的ETF**、**港股通市值前100**，并计算：

- 日线 / 周线 / 月线 **KDJ 的 J 值**
- **MA20 / MA60 双均线状态**（多头/空头排列）、价距MA20%、量比
- 当前 **PE_TTM、PB_MRQ** 及其 **历史分位%**（全历史 + 近5年窗口）
- 所属**行业**（A股）

结果按日期输出到 `output\<日期>\` 目录，并发布为 GitHub Pages 站点。

> **这个项目的输出分两类，可信度完全不同**，读数前请先看
> [胜率基线与超额](#胜率基线与超额为什么每个胜率都必须并排给出基线)：
> **描述性**输出（J 值、均线状态、量比、估值分位、行业）经过逐字段核验，准确；
> **预测性**输出（"哪些策略胜率高"、任何形式的择时暗示）已被一次 527 个交易日的
> 回测**证伪**，因此项目里不再发布任何形式的"买入参考"。

## 每日输出（以 2026-07-19 为例）

- `output\2026-07-19\top100_2026-07-19.csv` — 市值前100
- `output\2026-07-19\metrics_2026-07-19.csv` — 指标结果（**源头数据**，入库）
- `output\2026-07-19\run_2026-07-19.log` — 运行日志（只记诊断，逐标的回显走 stdout）
- `output\2026-07-19\DONE` — 完成标记。**内容即体检报告**（status/rows/success_ratio/fill），
  只有数据质量门通过才会写入；工作流据此判断当天是否真的完成

**日报 HTML/MD 不入库**。它们是**派生数据**：`generate_report` 只依赖 metrics CSV，
所以 `build_pages.py` 在构建站点时用 `reports.ensure()` 现场物化。实测一次日常提交里
`.html` 占 2973/4014 行（74%）、按字节占已提交产物的 62%，而它们可以被完全重建。

这同时修掉一个隐蔽问题：把派生 HTML 入库，意味着**代码修好后归档页会一直停留在
旧代码的输出上**。实测证据：`output/2026-10-09/report_*.html` 由 `7f98e25`
（10-10 00:06）提交，而 `market_insights.py` 的信号分类修复在 `ef20d2f`
（10-10 09:31）—— 晚了 5.5 小时，那份报告因此一直缺着修复后的板块分组。

`metrics` 字段：排名、代码、名称、日线J、周线J、月线J、最新价、涨跌幅、PE_TTM、PE历史分位%、PB_MRQ、PB历史分位%、MA20、MA60、双均线多头、价距MA20%、量比、PE5年分位%、PB5年分位%、行业

## 运维须知

几个每天都会用到、但踩过坑才写下来的规则：

- **「目标交易日」而不是「今天」**：`trading_calendar.py` 是**唯一**判断入口
  （workflow、三个 runner 都调它）。它同时回答两个不同的问题：

  | 问题 | 函数 | 用途 |
  | --- | --- | --- |
  | 现在该采集哪一天？ | `collection_target()` | 决定三个 runner 跑不跑、跑哪一天 |
  | 哪一天必须已经有数据？ | `latest_closed_trading_day()` | 决定 workflow 判红还是判绿 |

  两者在盘中是**不同**的，把它们混为一谈正是 2026-09 丢掉 8 个交易日的原因：
  当时用「今天 + `hour < 15`」判断，而 GitHub 的 schedule 实测**延迟中位数 4.64 小时、
  最大 7.80 小时**（北京的 16:30 触发点常在次日 00:00~02:00 才落地）。跨过午夜后
  「今天」变成了第二天、小时数是 0，于是判「未到收盘」直接跳过，gate 又把这次跳过当成
  「非交易日」放行 —— **整天数据静默丢失，而 Actions 全绿**。

  现在改为「最近一个已收盘、且其收盘价仍是数据源最新一根 K 线的交易日」：

  | 时刻 | 目标日 | 采集 |
  | --- | --- | --- |
  | 当天 23:46 | 当天 | ✅ |
  | 次日 01:00 / 08:00 | **仍是前一天** | ✅（跨午夜不再是歧义，反而成了补跑窗口） |
  | 次日 10:00 | 前一天 | ❌ 拒绝：最新一根 K 线已是当日实时 bar |
  | 周六/节假日 | 节前最后一个交易日 | ✅ |

  最后一行是 gate 自动绿灯的原因：节假日时「必须有的那天」= 节前最后一个交易日，
  它的 DONE 早就存在。而「因为故障没跑」会实打实地判红。
  年度表需每年按上交所/深交所休市公告更新（`A_SHARE_HOLIDAYS` /
  `HK_EXTRA_HOLIDAYS`，港股通为两者并集）；未覆盖年份 fail-open 放行 + 告警。
  本地验证：`DSM_CALENDAR_NOW=2026-10-09T01:00 python trading_calendar.py plan`。
- **每一行都记录自己的数据日期**：`metrics_*.csv` 的 `数据日期` 列写的是这一行
  实际取自哪一根 K 线，质量门会拿它和目标交易日比对。这是 2026-10-02 那次事故的
  补丁 —— 国庆休市，但旧版 workflow 不知道，把 09-30 的收盘价当成 10-02 发布了出去
  并写了 DONE。只校验行数/填充率是抓不住「数据完好、只是日期错了」的。
- **东财会按 IP 整批拒绝**：`push2*.eastmoney.com`（列表/排行接口）对云厂商出口 IP
  会直接 RST —— 实测 4 个主机、12 次重试全部 `RemoteDisconnected`，而同一时刻
  `datacenter-web`（估值）、腾讯 K 线、`quote.eastmoney.com` 都正常。这是
  **主机级、非瞬时**的封锁，指数退避对它没有任何价值。所以：
  - `http_util.HostPool` 让连续失败的主机**退役**，把最坏耗时从 351 秒压到约 45 秒；
    快速失败是为了把机会让给**不同时刻**的重试 —— 也就是**下一个触发点**。
    这里曾经有一个 CI 内的「3 轮重试未完成市场」步骤（每轮 `sleep 180`，最多再
    全量重采 9 次），实测**一次都没救回过运行**：抽样 3 个失败运行全部是
    「第 1 轮重试后仍缺 → 第 2 轮重试后仍缺」，因为它的 sleep 180 与封禁窗口
    是同一个 10 分钟。已删除，失败运行耗时从 5~10 分钟降到 2 分钟以内。
  - **「取名单」步骤有自己的硬预算**（`DSM_LIST_DEADLINE_SEC`，默认 45 秒）。
    这是一笔实测出来的账：2026-10-09 三次 A 股运行里，取名单分别花掉
    **348s / 348s / 259s**，而整个「抓 113 只标的的指标」只花了 **52s** ——
    一轮运行 73% 的时间在等一份**成分名单**。名单失败本来就有降级路径，
    所以超预算立刻降级，把重试留给下一个触发点。同时把名单请求的轮次
    从 4 主机 × 2 轮压到 4 主机 × 1 轮（代码自己的结论就是这种重试价值≈0），
    读超时从 15s 收到 8s。
  - 三个「取列表」的步骤都有**降级路径**：接口不可用时改用观察池历史名单
    （`stock_pool.list_from_pool`）。成分日间变化极小，而**指标仍然全部实抓**，
    所以降级只影响「今天谁算 Top100」，不影响任何一行指标。DONE 里会记
    `universe=pool-fallback`。
  - 三个取列表的调用点原来传的是 `requests` **模块**而不是 `Session`，
    而 `requests.get()` 内部会 `with Session()` —— 每次重试都新建连接、重做 TLS
    握手，连接池完全失效。现在 `get_json` 会直接拒绝模块，堵死这个坑。
- **必须限流，否则腾讯也会封你**：`fetch_metrics` 是 8 线程并发，原来每标的抓
  **3 个周期**（≈340 次请求）且只有**每线程** `sleep(0.15)`，合起来约 50 次/秒 ——
  实测直接把腾讯打到限流（响应变非 JSON），随后**113 只标的全灭**。
  现在两件事都改了：
  1. **只抓日线**，周线/月线在本地聚合（`fetch_metrics.resample_period`）。
     请求数 339 → 113，仅全局限流的下限就从 102 秒降到 34 秒。
     实测 113 只标的从 52s 降到 **35s**（本机、`DSM_REQUEST_INTERVAL=0.30`）。
     等价性有专门的守卫：`tests/test_kline_agg.py` 用冻结夹具断言
     「日线 800 根 → 聚合 → 周/月 J」与腾讯周/月线接口**逐只相同**，
     并用当日生产归档做过端到端核验（见下）。
  2. `http_util.RateLimiter` 提供**跨线程**的全局最小间隔，默认 0.30 秒
     （≈3.3 次/秒，这是生产上长期验证过的速率，刻意不再调小）。
     `fetch_kline` 也补上了真正的退避重试（原来是 `retries=1` + 不 sleep 的
     双 host 循环，等于没有重试）。全军覆没时会抛自解释的错误，
     而不是让下游在「CSV 不存在」上崩掉。

  > **日线聚合的验收记录**（这是本次改动唯一有说服力的证据）：
  > 用新代码重跑 2026-10-09 的 113 只标的，与**当日生产归档**的
  > `metrics_2026-10-09.csv` 逐列逐格比对：
  > 排名 / 日线J / 周线J / 昨日日线J / 昨日周线J / 最新价 / 涨跌幅 /
  > PE_TTM / PE历史分位% / PB_MRQ / PB历史分位% / MA20 / MA60 / 双均线多头 /
  > 价距MA20% / 量比 / 量比30 / 成交额(亿) / PE5年分位% / PB5年分位%
  > —— **全部 100% 逐格相同（最大绝对差 0.00）**。
  > 只有月线 J 有 6/226 格差 **0.01**：接口值由最多 302 根月 bar 算出，
  > 本地由 38 根（800 根日线的上限）算出，K/D 是 alpha=1/3 的 EMA，
  > 种子权重衰减到 1e-7 量级 —— 恰好落在两位小数的进位边界上时会翻最后一位。
  > 这是可解释、有界的（≤0.01），不是口径漂移。
- **站点缺数据必须看得见**：`build_pages.py` 会比对「最近一个已收盘交易日」，
  缺哪个市场就在首页挂一条红色「数据已过期」横幅。站点也**总是**部署 ——
  旧版要求三个市场全部完成才发布，结果是「A股天天成功、ETF/港股被拦」时
  站点整整三周停在 2026-09-18：有数据却不给看，比缺一块更糟。
- **历史回填**：`backfill.py` 用历史 K 线 + 历史估值序列重算缺失交易日。
  指标公式只依赖「截至当日的序列」（`kdj_j`/`ma_values`/`volume_ratio` 都取
  `iloc[-1]`，`percentile` 取 `(series <= value).mean()`），所以把序列切到
  `date <= D` 得到的**就是 D 日收盘后的口径**，不是近似。
  A 股还会用估值接口的历史 `TOTAL_MARKET_CAP` 重建**当日真实的市值前 100**。
  港股/ETF 没有历史估值与市值，PE/PB 留空、排名沿用观察池顺序（与它们正常
  运行时的口径一致）。回填出来的 DONE 带 `backfilled=true`，不冒充实抓。

  ```powershell
  python backfill.py --all --from 2026-09-21 --to 2026-10-08 --dry-run
  python backfill.py --all --from 2026-09-21 --to 2026-10-08
  ```
- **产物保留：站点 30 天 + 统计历史 21 天 = 51 个交易日**。`prune_outputs.py`
  默认保留 `DSM_KEEP_DAYS`(30) + `HISTORY_DAYS`(21)，裁剪用 `git rm`（同时删索引与工作区）。
  （`output/stock_charts.html` 与生成它的 `generate_stock_charts.py` 已整体删除：
  336 行代码、1.97 MB、站点零引用、也不入库 —— 每天写一个没人看的 2MB 文件。）

  为什么必须多留 21 天：站点归档要展示 30 天，而重建归档报告需要
  `strategy_summary` 的 20 日滚动胜率窗口。只留 30 天时，最老那几天重建出来会
  退化成「历史不足」—— 实测已提交的 2026-09-18 港股报告写着「近20日胜率 49%，
  样本68」，重建却变成「历史不足：仅 20 个交易日」。多出的 21 天只作为**统计
  历史**，不出现在站点上（站点窗口由 `build_pages.MAX_DAYS = DSM_KEEP_DAYS` 控制）。
- **等待预算**：各步骤通过 `DSM_DEADLINE_SEC` 限制最长等待，超出即抛
  `DeadlineExceeded` → 不写 DONE → 由下一个触发点补跑，
  而不是在里面死等到 job 超时。「取名单」另有一个更紧的独立预算
  （`DSM_LIST_DEADLINE_SEC`，见上）。
- **价格源只有腾讯一个，而且它也会挂**：腾讯对云厂商出口 IP 会返回
  `501 + JS 挑战页`（body 是 `var i=location.href;var v=window.bt...`）。
  此时**整条链路一个交易日都跑不出来** —— 2026-10-09 的 ETF/港股就是这么丢的。
  这不是「重试就好」的故障，所以正确行为是**如实失败**：不写 DONE → gate 判红 →
  站点挂红色横幅 → 下一个触发点（不同时刻）再试。缺一天数据，好过发布一天错数据。

  > **试过新浪日线，结论是「不能用」。** 它看起来像现成的替代源（接口稳定、
  > 支持 A 股与 ETF、`datalen` 可到 2000），但**它返回的是不复权价**，
  > 而本项目全程用前复权。实测 601398 在 2023-06-19：新浪 4.83、腾讯前复权
  > 3.602（比值 0.746 ≈ 三年累计分红），而 2026-09-18 两边都是 8.07 ——
  > 近期恰好重合，因为复权因子在近期 ≈1。后果是：`日线J` 完全一致（9 日窗口），
  > 但 **`月线J` 差 1.4**（9 个月窗口跨了分红），足以把「超买/超卖」的分类翻掉。
  > 那正是本项目刚修掉的那类「静默发布错数据」，所以没有采用。
  >
  > 真要做的话，正确路径是：取东财 `RPT_SHAREBONUS_DET` 的分红/除权记录，
  > 自己按「每次除权把之前的价格乘以 (C−D)/C」重建前复权序列，再用现成的
  > 验收方式收尾 —— 「按截至某日重算，与当日实抓归档逐字段比对」
  > （回填就是这么验的，95% 逐位一致）。另外新浪**不提供港股通 K 线**，
  > 港股没有这条路。
- **外部 cron 的 PAT 权限**：外部触发服务（见「触发方式」一节）需要一个
  **fine-grained PAT**，权限为 `Actions: Read and write`（对 `logic77lhl/daily-stock-metrics`
  这一个仓库）。只读权限会拿到 403，而 `workflow_dispatch` 的 403 与「成功」在
  某些客户端里都表现为一个 2xx/3xx —— 所以配好后**必须手动验证一次真的跑起来了**，
  不要只看返回码。
  （原来这里还有一个 `heartbeat.yml` 用 `HEARTBEAT_TOKEN` 反向补触发。它已被删除：
  它自己也是一个被延迟 4~8 小时的 cron，用「一个不准时的定时器去补救另一个不准时的
  定时器」，而且它把触发次数从 6 次推到了 10 次。）
- **失败诊断要留痕**：workflow 会把 `run_*.log` 与 `failed_*.csv` 作为 artifact
  上传（保留 14 天）。fetch 层的重试明细以前只进 stdout，仓库里的 `run_*.log`
  只有三行，事后完全无法判断「重试了几次、哪个主机失败」。
  **落盘日志只记诊断**：逐标的的完成回显（`[ 12] 600000 … 日J=… MA20=…`）改为
  只进 stdout —— 它是 metrics CSV 的重复抄写，实测占了落盘日志 143 行里的 113 行
  （约 17KB / 22.7KB），却把真正的诊断淹没。现在落盘日志约 20 行。
- **历史面板必须时点隔离**：`strategy_summary._load_history(as_of=...)` 只使用
  `<= as_of` 的日期。没有它，重建一份历史报告会读到**报告日之后**才产生的行情，
  把「当时不可能知道的胜率」写进归档页。实测这个前视是真实存在的：不隔离时重建
  2026-09-18 的报告会读到 2026-10-08（29 个交易日），而「近 20 日胜率」的窗口
  需要的是 08-19~09-17 —— 整个窗口都落在报告日之后。
- **完成门会检查历史空洞**（`gate.py`，workflow 里唯一的红/绿裁决点）。
  它回答两个问题：目标交易日有没有有效 DONE，以及**最近 `DSM_GATE_LOOKBACK`
  （默认 5）个交易日里有没有空洞**。

  为什么需要第二问：旧版只校验「最近一个交易日」。某天一旦**永久丢失**，它只在
  当天被判红；之后目标日往前滚动，那天就再也不会被检查 —— 缺口永远留在站点上
  而 CI 全绿。这与 2026-09 静默停摆三周是同一类缺陷，只是窗口从三周缩到了一天。

  窗口取小值是**有意**的：窗口内的缺口几乎总能靠 `backfill.py` 补回来，所以判红
  是有意义、可自愈的；更老的缺口会滑出窗口，交给站点首页的红色横幅呈现。

  空洞的判据锚在 **metrics CSV** 上，不是 DONE 的格式：DONE 在 2026-09-21 变过
  一次格式（旧版只有一个时间戳、19 字节；新版是 `status=ok` 的体检报告）。实测
  用 DONE 判空洞会把 08-21~09-18 这 21 个旧格式日**全部误判成缺失**，让完成门在
  正确的数据上永远判红。所以：目标日用 `quality.done_is_valid()`（它证明质量门
  真的跑过），历史空洞用「CSV 在不在、行数够不够、`数据日期` 对不对」。

  本地可直接跑：

  ```powershell
  python gate.py --expected-a 2026-10-09 --expected-hk 2026-10-09   # 人读
  python gate.py --expected-a 2026-10-09 --expected-hk 2026-10-09 --json  # 机器读
  ```

  `gate.py` 也是**唯一**的裁决实现（原来「哪些市场缺数据」的循环在仓库里有三处
  拷贝，其中两处在 shell 里）。
- **workflow YAML 结构守卫**：`tests/test_workflows.py` 会检查 `run: |` 块有没有
  被顶格内容截断（内联多行 Python 最容易踩）。这不是洁癖：块被截断会让**整份
  workflow 非法**，GitHub 以「workflow file issue」在 0 秒失败且日志为空 ——
  此后所有定时采集静默停摆。守卫带自证测试（喂一份坏写法，必须被抓到）。
- **候选池与页面体积**：首页体积约为 `1.1 KB × 候选池上限`，调大
  `max_candidates` 时请一并留意仓库体积。

## 回测

```powershell
python backtest.py                       # 全市场
python backtest.py --market 个股 --horizons 1,5 --cost 0.15
python backtest.py --strategy "自定义=日线J<20 and MA20>MA60"
python backtest.py --bars 800            # 每只标的多长价格序列（影响缓存键）
```

- 内置策略含：双均线多/空头、价上MA20且多头排列、KDJ三周期共振/分化、超卖+多头排列、低位放量等组合
- 价格统一采用**最新前复权序列**重建（跨日可比），缓存在 `backtest_results/kline_cache/`

### 成交价口径（2026-10 修正前视偏差）

原来的成交价是**信号日收盘价**，而所有信号（`日线J`/`MA20`/`MA60`/`量比`/`PE历史分位%`）
都由**同一根收盘价**算出 —— 「收盘后才知道信号，却按收盘价成交」，是前视偏差。
现在改为：

```
T 日收盘后出信号  →  T+1 开盘价建仓  →  持有 h 个交易日后收盘平仓
```

实测影响（同一批 44523 个策略×交易样本，逐笔配对，0 未匹配）：**胜率下降 0.5~4pp**，
平均收益下降 0.03~0.16pp。KDJ 均值回复类策略受影响最大
（`三周期共振偏弱` h=3 从 +0.13% 翻负到 +0.04%；`超卖+多头排列` h=1 胜率 44.0%→39.6%）。
被去掉的隔夜跳空在这个样本里值约 +0.10pp/笔。

### 已知偏差（报告页脚「方法与局限」里逐条披露）

- **幸存者偏差**：面板来自每日「市值前 100 + 观察池」，而观察池 365 天不出现即剔除，
  退市/长期下跌的标的被系统性移除；从未进入过 Top100 的标的也完全不在样本内。
- **成本口径**：`(卖出×(1-c)) / (买入×(1+c)) - 1`，`c` 默认 0.15% 单边。
  对 A 股大盘股勉强够，**对港股通偏低**（还有印花税/交易征费/结算费）。
- **重叠持有期**：h>1 时「不重叠累计净值」按 h 日切桶复利（h=1 与旧的日频复利一致）；
  旧实现把重叠持仓重复计入，会明显高估净值。
- **样本窗口**：交易必须在面板覆盖的最后一个**真实交易日**内完成，
  否则计入 `skip_horizon_beyond_panel`。这让数字可以从已提交的产物复现。
- 每个被剔除的样本都有计数器（`drop_no_price_series` / `drop_no_entry_bar` /
  `drop_no_exit_bar` / `drop_bad_price` 等），会打印并在报告里列表，不再静默丢弃。

- 价格序列的新鲜度门槛是「必须覆盖面板要求的最后一个交易日」（原来只是「5 个自然日内」，
  隔几天再跑就会拿旧价配新指标）；缓存键含 `bars`，且拒绝只存 close 的旧格式缓存。
- 收益已按 `--cost` 单边成本扣减（默认0.15%，覆盖佣金+税费+滑点），
  页面上的买入价/卖出价保留 3 位小数且收益由这两个价复算，**可手工验算**。

## 胜率基线与超额（为什么每个胜率都必须并排给出基线）

**只发布「胜率 55%」而不发布「同期全样本 47%」，是主动误导。** 这个项目的报告、
站点和邮件里所有胜率现在都并排给出基线，`backtest.py` 的汇总表还额外给出
`超额胜率(pp)` 与 `超额收益%` 两列。

基线就是内置策略表里的第一项 `全样本(基准)`（`expr=None`，不做任何筛选），
所以它的收益是「同期同标的的等权平均」—— 唯一正确的对照。本样本的实测基线是：

| 持有期 | 全样本胜率 | 全样本平均收益 |
| --- | --- | --- |
| 1 日 | **47.18%** | +0.0534%（中位数 **−0.0475%**） |
| 20 日 | 48.67% | +1.1861% |

注意 1 日的中位收益是**负的**、胜率低于 50% —— 收益全部来自右尾。在一个基线
47% 的样本里，「55%」和「47%」的差别没有意义，而它看起来像"好"。

### 独立回测的结论（527 个交易日，2024-07 ~ 2026-10）

为了判断「到底哪些功能是有意义的」，做过一次独立回测：逐日重建**当日真实市值
前 100** 的横截面（不是用今天的排名回测过去），56 个假设，
Fama-MacBeth 按日聚类 + Newey-West 校正，T+1 开盘建仓，Bonferroni 校正：

- **56 个假设无一通过 Bonferroni 校正**（阈值 |t| > 5.32），全场最大 |t| 仅 **3.16**；
  |t| > 2 的个数（3/5/3/4/1，按持有期）**低于或等于**纯随机期望 2.8。
  「|t|>2 的个数 ≤ 随机期望」比「没通过校正」更能说明问题：真有信号时这个数
  应该明显超过 2.8。
- **核心假设方向是反的**：按当日 J 的横截面十分位分组，低 J 组（D1）在所有持有期
  都是**负**超额（−0.073 / −0.179 / −0.174 / −0.366 / −0.600，h=1/3/5/10/20），
  而高 J 组在 h=10/20 是**正**超额。这个样本里是动量，不是均值回归。
  三个旗舰信号全是负的：三周期共振超卖 −0.164（t=−2.51）、
  超卖+多头排列 −0.096、低位+放量 −0.107。
- **最小可检测效应**：h=1 时 0.118%/日（≈29%/年）。A 股单次往返成本约
  0.12%~0.22%，而本研究里**最大**的日均超额是 0.127%（t=1.01，不显著）——
  **没有任何信号接近覆盖成本**。

### 被删除的「今日买入参考」

它曾是一个跨市场功能：按滚动胜率选出标的、发一封邮件、写
`recommend_history.json`、在站点上占一个页面、并在每份报告底部追加「往期推荐复盘」。
527 个交易日的回测**证伪了它的机制**（不是"参数没调好"）：

| 检验 | 结果 |
| --- | --- |
| 入选组合的跟踪期胜率 | 53.85%（全部 46.72%）→ 机制确实挑出了"过去赢"的 |
| 入选组合的次日平均收益 | **+0.0289%**（全部 +0.0612%，随机 3 只 +0.0530%） |
| 入选组合跑赢"随机 3 只"的日期比例 | **49.7%**（无技能应为 50%） |
| 「跟踪 20 日胜率」与「之后 20 日胜率」的自相关 | r = +0.0214（t=1.09） |
| 选择技能 | −0.0323%（t=−0.86） |

也就是说：它稳定地选到了「过去赢、接下来输」的标的，而胜率本身不持续。
**这个机制在原理上不可能有效。** 整块（`run_buy_daily.py`、`build_buy_list`、
`buylist.html`、`recommend_history.json`、复盘、`摘要-买入参考.md`）已删除。

同时删掉的还有 `backtest.py` 报告里的「⭐ 重点策略参考（按 3 日胜率取前 3）」
卡片区，以及首页的「持有 1 天/3 天最佳策略」卡片 —— 在一个基线 47%、
56 个假设无一通过校正的样本里，"前 3 名"就是噪声排序，而 ⭐ 与「今日信号 N 笔」
的措辞会让它看起来像被筛选过的机会。汇总表仍然逐行给出全部策略 × 持有期。

### 本研究没有回答的问题（限制）

1. **只有一个市场状态**（2024-07 ~ 2026-10，样本内累计 +26.98%）。
2. **只覆盖市值前 100 的大盘股**。信号在小盘股上可能有效，**没有检验**。
3. **未计交易成本**（第 4 节单独讨论了成本门槛）。
4. 月线 J 预热不足：腾讯日线上限 800 根 ≈ 38 个月 bar。
5. 56 个假设的 Bonferroni 是**保守**的；但它同时给出「|t|>2 的个数 ≤ 随机期望」
   这个不依赖校正的判据，两者结论一致。

## 触发方式

**主触发是外部的免费 cron 服务直接打 `workflow_dispatch`**，不是 GitHub 的 `schedule`。

### 为什么不用 GitHub 的 schedule

`schedule` 是 best-effort，实测**延迟中位数 4.64 小时、最大 7.80 小时**
（对 52 次可归因的 daily-metrics 运行统计；2026-10 已经出现 9.1 小时的样本）。
它根本不适合「收盘后尽快出数据」这个需求。

原来的应对是**堆触发点**：6 个 cron + `heartbeat.yml` 的 4 个 = **每天 10 次触发**，
去追一个 4~8 小时的抖动。代价不是运行时间，而是**信噪比**：10 次里有 9 次只是撞上
「今天已完成，跳过」，于是 Actions 历史里全是噪声，真正的红灯（数据确实缺了）
被淹没在里面。而 `heartbeat.yml` 本身也是一个被同样延迟的 cron —— 用「一个不准时的
定时器去补救另一个不准时的定时器」。

`workflow_dispatch` 是唯一不受这个抖动影响的入口：实测 `createdAt == startedAt`
（**秒级**启动）。所以触发时刻完全由我们决定 —— 这正是原来想要、而 `schedule`
给不了的东西。

### 怎么配（一次，5 分钟）

1. 建一个 **fine-grained PAT**：Settings → Developer settings → Personal access tokens
   → Fine-grained tokens。仓库选 `logic77lhl/daily-stock-metrics`，
   权限 `Actions: Read and write`。记下 token。
2. 在任意免费的定时服务（例如 cron-job.org）建一个任务：
   - URL：`https://api.github.com/repos/logic77lhl/daily-stock-metrics/actions/workflows/daily.yml/dispatches`
   - Method：`POST`
   - Headers：
     ```
     Authorization: Bearer <你的 PAT>
     Accept: application/vnd.github+json
     Content-Type: application/json
     ```
   - Body：`{"ref":"main"}`
   - 时间：**工作日北京时间 16:35**（A股 15:00、港股 16:00 都已收盘）
3. **手动点一次 Run now，然后去 Actions 页面确认真的跑起来了**。403（权限不足）
   在某些客户端里不会表现为失败，只看返回码会被骗。

### 兜底

`daily.yml` 里保留了**一个** `schedule`（北京时间次日 01:00）作为纯兜底：
万一外部 cron 服务挂了或 token 过期，数据不至于整天不更新。
这一档实测最准时（延迟 0.04~0.70 小时）。`DONE` 防重保证它与外部触发不会重复采集。

- **流程**：A股 → ETF → 港股 → 回测 → 价值标的 → 裁剪 → 建站 → 提交 → 部署 → 完成门
- **邮件**：3 封市场报告（A股 / ETF / 港股通），每封含「📌 今日速览」，
  速览里的胜率**并排给出基线**（见 [胜率基线与超额](#胜率基线与超额为什么每个胜率都必须并排给出基线)）
- **GitHub 预览**：根目录 `摘要-A股.md` / `摘要-ETF.md` / `摘要-港股.md` 每日自动更新。
  各日期目录下的 `report_日期.md` / `report_日期.html` 仍会生成（邮件与站点都用它），
  但**不入库** —— 它们是派生数据，由 `build_pages.py` 从 metrics CSV 现场重建。
- **手机适配**：报告 HTML 已针对移动端优化（窄屏字体/布局自适应）
- **手动触发**：仓库页 Actions → daily-metrics → Run workflow
  （`mode=site-only` 只重建并部署站点，不重新采集）
- **日志查看**：Actions 运行记录里可看每步输出
- **邮件配置**：通过仓库 Secrets（`SENDER_EMAIL` / `SENDER_AUTH_CODE` / `RECIPIENT_EMAIL`）注入，
  本地运行则读取同名用户环境变量

本地与云端互为备份：本机自启动若当天已跑完（DONE 标记在本地），云端仍会独立跑一遍并提交结果。
